## 一、磁盘与运行时治理（已完成）

**问题链**：知识库上传时报"解析失败" → 逐层剥出：

| 层 | 现象 | 根因 | 处置 |
|---|---|---|---|

| 能力层 | "无法从文档中提取有效文本，请确保内容非纯图像" | **v2.7.0 入库管线无 OCR** | 见下节 |

**磁盘账本**：C 盘 301G / D 盘 652G 均紧张。C 盘首恶 = Docker 虚拟磁盘 `docker_data.vhdx` 81G（`C:\Users\anoth\AppData\Local\Docker\wsl\disk\`）。清理战果：构建缓存 17G、Temp 14G、回收站 4G+，C 盘可用 2.6G → 22G。**fstrim 已执行（标记 955.6GiB 空闲块），diskpart compact 待用户管理员执行**（需先 Quit Docker + `wsl --shutdown`）。

**Langfuse 定位**：调用链观测组件，不在任何主链路上，停掉零功能影响，可随时 `docker start` 恢复。建议正式评测期间保持停止以节省内存。

## 二、D02 图片轮：平台能力边界实证

**错误码代际**：`no_valid_chunks` / `Ray processing completed but produced 0 chunks` / `file_process returned empty list for source='D02_ownership_diagram.pdf'`。

**结论**：Nexent v2.7.0 知识库入库管线只做文本提取，**没有 OCR**，纯图像 PDF 必然失败。这是设计取舍不是缺陷——OCR 的时间/算力/费用/质量四项成本都比文本提取高两三个数量级，且错误文本入库会污染检索。

**为什么"配了多模态模型还是不能识别"**：平台的**两条链路是分开的**——
- 对话链路：用户消息+附件 → 多模态模型看图 → 回答（多模态模型在这条线上）
- 入库链路：文件 → 文本提取 → 切片 → Embedding → ES（这条线上没有任何环节会看图）

入库是批量后台任务，把多模态调用塞进去会让时间和费用爆炸，所以平台把视觉能力分配给了交互式对话链路。

**三条优化路线（决议）**：
| 路线 | 做法 | 代价 | 决议 |
|---|---|---|---|
| A 外挂预处理 | 自己脚本：PDF 渲染成图 → 调多模态 API/OCR → 生成文字层再入库 | 半天 | **主轨** |
| B MCP 读图工具 | 写"图片理解"MCP 工具，Agent 通过 MCP 读原图 | 1–2 天 | **亮点轨** |
| C 改 data-process 源码加 OCR | 改 Ray actor 加 OCR 分支、重建镜像 | 一周起 | **竞赛期间不做**（破坏评测环境一致性、赛题不考改平台、时间不够）；改为赛后给社区提 issue |

## 三、知识图谱概念澄清（配图见 docs/design/03-ontology-diagram.png）

- **本体（ontology）**= 骨架、类别模板：有哪些实体类型、什么属性、什么关系。举例：公司（名称/持股比例）、担保合同（编号/金额/时点）、授权决议（版本/生效期/上限）。人工半天可定，**跨公司跨行业可复用**。数据库类比：表结构（表头）。
- **知识图谱**= 按骨架填好的实例网络，含具体数字。举例：A公司—持股80%→甲公司、A公司—担保3000万→G01合同。数据库类比：表里的一行行数据。
- **半自动化**= 机器填草稿、人只审重点。五步流水线：行业文档 → 机器抽候选三元组（每条带页码出处）→ 机器按"分歧×影响×成本"排序 → 人工只审 Top-K（属实准入/存疑驳回）→ 入图谱。省下的是**专家时间**，这是低资源场景最贵的资源。
- 真实例子：候选#7（乙公司,持股,40%）出处 D02 第1页 → 人工核对属实 → 准入；候选#12（A公司,授权担保,乙公司1000万）→ 查无授权依据 → 驳回并登记为证据缺口。

## 四、"低资源场景"如何理解

不是数据少，是**贵的东西少**：人工标注、专家审核时间、微调算力都缺。高资源路线靠买数/标注/训模型；低资源路线靠**公开资料 + 少量种子本体 + 运行时检索（RAG，不训练）**。

低资源解法一句话：**机器做抽取和初筛（便宜、量大），人只做高价值决策（贵、量少），并证明这个分配优于乱分配**。

本项目实证：无行业数据→改用公开资料（10-22 决策）；D01–D08 合成资料 + 人工定义担保概念 = 种子；候选审核优先级公式（抽取分歧 × 影响业务问题数 × 冲突程度 × 人工成本）。**A5 对照实验（随机 vs 不确定性 vs 业务影响优先）是这条命题的直接证据，目前缺数据。**

## 五、"知识体系更新迭代快"如何处理

**固定知识库的四个死穴**：新标准来了旧结论不死；删除/修订无机制；知识间有依赖但无影响传播；业务标准自带时间轴但库没有时间概念。

**四层解法（本项目已实证三层）**：
| 层 | 做法 | 实证 |
|---|---|---|
| ① 知识带时间轴 | 每条事实/规则带生效起止，按时点筛 | C07/C08：A1 到 6/30、A2 自 7/1 不追溯 |
| ② 历史快照不覆盖 | 新事实追加、旧结论不改写、冲突并列 | C06 冲突双值并列；C08 历史余额不回填 0 |
| ③ 三种更新分开 | 事实更新 / 规则更新 / 本体结构更新 分流 | C08 a 轮"不足以决定改结构，先 gap analysis" |
| ④ 变更影响定位（待建） | 新标准进入→沿依赖找受影响结论→只重算这部分 | 单点已验（C08），自动化即"说明书修订影响定位"方案 |

合起来就是赛题标题的"**可进化**"：建得省（低资源）+ 活得久（动态更新）。

## 六、行业数据价值激活 + 智能化业务编排

**激活三步**：① 资产标识（盘点、打标 ID/类型/版本/来源、入清单）→ ② 认知加工（识别、抽取、入知识库/图谱、附证据位置）→ ③ 价值闭环（业务问题进、带证据结论出、决策可溯源）。本项目三步都有实证，度量三维：正确率（T 系列 10/10）、溯源率（100% 带页码）、缺证诚实度（C05 保留判断）。

**智能编排 vs 传统 workflow**：传统是人把流程写死；智能编排是运行时由智能体决定拆什么条件、检索什么、调哪个工具、哪里缺证就停、哪里转人工。

执行流五段：业务问题 → 拆待验证条件 → 并行检索+确定性工具 → 汇聚校验（单位/去重/口径/时点）→ 缺口分流（改写重检/待补保留/提交本体候选）→ 带证据页码输出。

两个编排层次：执行流（运行时，C08 a 轮是完整实录）；能力编排（构建时，固化成 Skill 模板，换语料即跨行业）。

## 八、赛题措辞拆解：多模态异构 / 认知智能体 / 资产标识

- **多模态异构**：文本、表格、图文混排、音视频一起处理，且同类信息格式各异（"3,000万元" vs "30,000,000元" vs 藏表格合计行）。要求能识别同一事实的多种表述。本项目已踩坑：D02 纯图像 PDF、C02 单位换算、C06 重复披露。
- **认知智能体**：五层能力感知→理解→关联→推理→**反思**（知道自己缺什么并诚实说缺）。试金石一句：能不能说出"我知道什么、依据是什么、还缺什么"。本项目实证：C05 缺证保留、T04 口径消歧（63.94% 是资产负债率）、C07 时点推理、C06 冲突并列、a 轮检出重复入库。
- **资产标识**（题面原文是"标识"不是"表示"）：给每个数据对象上户口——唯一 ID、资产类型、业务含义、来源版本、质量状态、关联关系。本项目雏形：D01–D08 标识体系、asset_manifest.json、回答引用"资产标识：D03_balance_20260630"、D08 重复入库被检出（正说明标识缺失的后果）。区分："标识"=户口本；"表示"=内容的机器可读形式（向量、三元组）。
- **项目短板定位**：底层认知层要求"统一识别/理解/标识多模态异构数据"，上层是决策应用。本项目文本/表格已过、认知行为已实证，**唯一没过的是图像模态 + 手工 manifest 未自动化**——补这两项才真正贴合题面。

## 九、Nexent MCP 协议核心机制（源码实证）

**本质**：MCP = "AI 调外部能力的插座标准"，Nexent 基于 `FastMCP` 实现，并加了三样企业级改良。

**四层机制**：

1. **服务端两形态**
   - **OpenAPI → MCP 自动转换**：`backend/mcp_service.py:211 register_openapi_service()` → `FastMCP.from_openapi()`，企业现有 REST API 只需一份 OpenAPI spec 即可变 MCP 工具，零改造。（本项目做"担保计算器"就走这条）
   - **容器化 MCP**：`backend/services/mcp_container_service.py` 的 `MCPContainerManager`，用 Docker/K8s 起独立容器，支持 tar 镜像加载与端口映射；挂了不拖垮主系统。本地 `nexent-mcp` 容器即此层。
2. **传输层两方式**：`backend/services/remote_mcp_service.py:115` —— URL 以 `/sse` 结尾用 `SSETransport`，否则用 `StreamableHttpTransport`，自动识别。
3. **多租户隔离**：`TenantMCPRouter`（`mcp_service.py:444`）路由 `/mcp/{tenant_id}/...`；三选一鉴权（JWT 中 tenant_id 必须匹配路径 / 内部令牌 / 否则 403）；每租户独立 FastMCP 实例（`_tenant_mcp_servers`）懒加载。
4. **工具绑定"模板-实例"模型**：`ag_tool_info_t`（工具模板）+ `ag_tool_instance_t`（tool_id + agent_id + params + enabled）——同一工具不同 Agent 可配不同参数。

**Skill 层（与 MCP 分工）**：
| | MCP | Skill |
|---|---|---|
| 是什么 | 单个原子能力 | 整套流程包（zip：SKILL.md + 提示词 + 工具配置） |
| 存储 | `ag_tool_info_t` / 实例表 | `ag_skill_repository_t`（`skill_zip_base64` + `skill_info_json`） |
| 分发 | 市场（官方/社区） | 有市场：分类、标签、下载量、官方认证 |
| 谁生成 | 人工或 OpenAPI 转换 | `nl2skill_agent`：自然语言生成（临时 Agent，max_steps=5，无持久状态） |

**三层编排**：底层 MCP 提供零件、中层 Skill 给出装配图纸、顶层 Agent 决定这次装什么。

**答辩表述三要点**：①MCP 把 N×M 集成问题压成 N+M（每家系统出一份服务、每个 Agent 说一种协议）；②Nexent 在标准之上加了租户隔离、容器化托管、模板/实例分离，这是与裸 MCP 的差别；③Skill 与 MCP 是"流程 vs 零件"，只堆工具是"能调"，沉淀成 Skill 才是"能力沉淀/可复用模板"（对应评分原文）。

**源码自查路径**：`backend/mcp_service.py`（转换+路由）、`backend/services/mcp_container_service.py`（容器）、`backend/services/remote_mcp_service.py:115`（传输）、`backend/apps/skill_app.py`（Skill 接口）、`backend/agents/nl2skill_agent.py`（NL2Skill）。

## 十、本次会话涉及的工程经验（可复用于答辩"调试迭代经验"）

1. **三层排查法**：服务层 → 资源层 → 能力层，每一层用日志实锤定位，不猜。
2. **错误信息会随时间演进**：同一个"解析失败"，前后三次给出三种错误码，说明每次修完一层后下一层才暴露——排查要有耐心分层，不要一次改多个变量。
3. **对话记录从数据库捞**比让用户复制可靠：`conversation_message_t` 直查（`delete_flag='N'`）。
4. **原生产路线判死也要留证据**：错误码 + 日志原文 + 平台边界说明，比"试过了不行"有说服力。
5. **失败尝试必须归档**：用户曾删掉失败会话，导致无法回溯——已提醒写入规范。
